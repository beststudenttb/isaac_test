# Agent Project Rules

本文档记录 Codex、CC 等 agent 在本项目中的共同工作规则。若用户给出新的、更具体的要求，以用户最新要求为准，并及时更新本文档。

## 0. 最重要

- 每次上下文压缩、恢复或摘要接续后，agent 必须先重新读取 `./summary/agent_rule.md`，再继续任何实质性工作。
- 重新读取规则后，还必须读取 `./summary/readme.md` 和当日总结 `./summary/yyyy_mm_dd_{device}.md`；当对应文件不存在时跳过。
- 后面随时会有新增，新增规则时放入合适位置。

## 1. 协作原则

- 默认中文沟通，除非用户明确要求其他语言。
- 用户与 agent 是合作关系。agent 必须独立判断方案利弊和风险，不无条件接受用户想法，不使用未经判断的顺从式表达；若认同，说明具体理由。
- 用户描述有多义或指令模糊时，必须指出歧义并询问真实意图；能从上下文合理判断且风险不高时，直接推进。
- 读取、搜索、修改、测试等关键步骤中给出简短进度说明。
- 最终回复说明完成内容、验证情况、未完成事项或风险。

## 2. 文件与 Git 规则

- 不得回滚、覆盖、删除用户已有改动，除非用户明确要求。
- 删除、覆盖、强制回滚、不可逆迁移等操作，必须先说明对象、影响和风险，并获得用户明确同意。
- 修改前查看相关上下文，理解现有结构和风格；手动编辑用各自顺手、方便且不危险的工具，优先做最小化精确改动；搜索优先用专用搜索工具，避免用 cat/grep 通读大文件。
- 本项目由 Claude 和 Codex 共同开发，可能出现两个 agent 先后或并发修改同一文件。修改任何文件前，先用 git（如 `git status`、`git diff`）确认目标文件是否已有另一 agent 的未提交或新提交改动；若有，先纳入这些改动再动手，避免覆盖或改坏对方的工作。
- 不使用 `git reset --hard`、强制 checkout、无确认删除等破坏性命令，除非用户明确授权。
- 遇到脏工作区，只处理当前任务相关文件，不清理无关改动。
- 回答代码问题必须读取当前源码；若涉及项目内自定义导入，继续读取相关模块。官方库或 pip 包可基于已有知识回答，必要时查官方文档。
- 两个 agent 记忆不互通，所涉代码可能已被对方修改。回答代码相关问题前，先用 git 检查相关文件自上次了解后是否被改动；若被改动，必须先看对应 diff，必要时完整重读被修改的文件，确认实际现状后再作答，不得凭旧记忆回答。
- Webots 原项目 `../visual_rlrobot` 为只读参考源，移植时可读取对照，不得修改其任何文件；`visual_rlrobot2` 是唯一工作区。
- `typ`、`pdf`、`doc`、`docx` 等作业文档默认不上传 Git，除非用户明确要求。

## 3. 总结与路径规则

- 固定资源放 `./assets/`，例如机器人 USD、场景 USD、材质和模型文件。
- 可直接运行的脚本放 `./scripts/`，例如预览、性能测试、数据采集、导出工具；优先直接放在 `scripts` 根目录，不做多层脚本嵌套。
- 可复用项目逻辑放 `./src/`，例如环境创建、相机标签、reset、RL env 定义。
- 训练和评估入口放 `./train/`，由这里调用 `./src/` 里的逻辑。
- 项目总结类内容统一放在 `./summary/`。
- 规则文件固定为 `./summary/agent_rule.md`，供 Codex 和 CC 共同遵守。
- `./summary/readme.md` 记录项目最新状态，只保留仍然有效的当前信息；过时内容直接移除。
- 每日总结文件命名为 `yyyy_mm_dd_{device}.md`，`device` 从当前运行 Chat 的设备判断，只用 `ubuntu`、`mac`、`win`。
- 每日总结只记录当天与项目有关、实际推进过的内容；与项目无关的对话不写入。
- `./summary/TODO.md` 记录后续可能要做且现实可执行的想法；过于发散或暂时不可落地的想法不写入。
- 用户每天晚上要求总结并上传 Git 时，先更新当日总结、`readme.md` 和 `TODO.md`，再按用户确认的范围 push 到 Git。

## 4. 代码实现规则

- 本项目是研究/学习项目，不按生产工程方式过度设计。
- 遵循现有架构、命名、格式和工具链；改动保持最小，不做无关重构或不必要抽象。
- 不做过度防御性编程，不写自动找路径、自动加载模型、自动兼容目录结构等工程化兜底逻辑，除非用户明确要求。
- 模型、数据、配置等默认使用明确相对路径；文件名、模型名默认写死，保持逻辑直接一致。
- 函数、文件、变量命名简洁清楚，避免冗长。
- 结构化数据优先用可靠解析器或项目已有工具；注释只解释不明显逻辑。
- 默认使用 ASCII；只有文件已有风格或业务需要时才引入非 ASCII。

## 5. 测试与验证

- 完成代码改动后，尽量运行相关的最小验证；影响共享逻辑、用户流程或跨模块契约时扩大验证范围。
- 测试无法运行时，在最终回复说明原因和风险；不得把“未测试”说成“已验证”。
- agent 尽量在沙盒内运行，非必要不超出沙盒；确需超出沙盒，或需启动 Webots、Isaac Sim 等大型软件、图形环境或物理仿真器时，必须先获得用户同意。优先用轻量静态检查、单元脚本或代码阅读验证。
- 可视化产物（训练曲线、相机图、heatmap 等）需验证画面非空、构图与数值合理。

## 6. 依赖与环境

- 本项目默认使用 conda 环境 `isaac_test`。
- 不擅自安装依赖、拉取网络资源或改动全局环境；必要时先请求用户批准。
- 优先使用项目内已有脚本、配置和环境；不留下无关临时调试产物。

## 7. 安全边界

- 不泄露密钥、令牌、隐私数据或敏感文件内容。
- 外部事实、价格、法规、版本、新闻等可能变化的信息，先查证再回答。

## 8. 项目内优先级

当规则冲突时，按以下优先级执行：

1. 用户在当前对话中的明确要求。
2. 系统与开发者指令。
3. 本文件中的项目规则。
4. 项目已有代码风格和文档约定。
5. agent 的通用工程判断。
