# Shared Agent Rules

本文档只记录 Codex、CC 等 agent 需要共同遵守的项目协作规则。各 agent 的私有边界、沟通风格、历史纠偏和工具纪律放在各自私有规则文件中，不在本文档重复维护。

## 0. 最重要

- 每次上下文压缩、恢复或摘要接续后，先重读 `summary/agent_rule.md` 及各自私有规则，再继续实质性工作，不凭被压缩的摘要臆断规则。
- 重读规则后，再读 `summary/readme.md` 和当日总结 `summary/yyyy_mm_dd_{device}.md`；文件不存在则跳过。

## 1. 协作基本

- 默认中文沟通，除非用户明确要求其他语言。
- 用户的当前明确要求优先；遇到多义、模糊或高风险指令时，先说明歧义并请求更精确指令。
- agent 必须独立判断方案利弊，不无条件迎合用户；认同或反对都要给出具体理由。
- agent 之间也须独立判断，不因对方是 agent 就采信其方案，对其方案要审查理由。
- 不得把未验证的判断说成事实；不确定时明确说明，并通过源码、日志、官方资料或实验验证。
- 不得跳过必要的源码阅读、diff 检查、验证或问题分析。
- 读取、搜索、修改、测试等关键步骤中给出简短进度说明。

## 2. 文件与 Git

- 修改前先查看 `git status`；涉及目标文件时查看相关 diff，避免覆盖用户或其他 agent 的改动。
- 脏工作区中只处理当前任务相关文件，不清理无关改动。
- 不得回滚、覆盖、删除用户或其他 agent 的已有改动，除非用户明确要求。
- 删除、覆盖、强制回滚、不可逆迁移等操作，必须先说明对象、影响和风险，并获得用户明确同意。
- 不使用 `git reset --hard`、强制 checkout、无确认删除等破坏性命令，除非用户明确授权。
- `typ`、`pdf`、`doc`、`docx` 等作业文档默认不上传 Git，除非用户明确要求。
- **提交描述尽量详细，正文 200–300 字**（不含标题行）。目的：未来换 agent / 换对话时，只看提交历史就能知道这次到底做了什么、为什么做、结论是什么。至少覆盖：改了哪些文件/模块、动机或要解决的问题、关键实现或参数选择、实验/验证结果或结论、以及遗留问题或下一步。写清因果，不要只罗列文件名。用户特别要求简短时才例外。

## 3. 目录路径

- `scripts/` 放常用脚本入口，例如预览、性能测试、数据采集、导出工具；保持浅层，不做多层嵌套。
- `train/` 放常用训练和评估入口；保持浅层，由这里调用 `src/` 中的复用逻辑。
- `src/` 放可复用项目逻辑，例如环境、相机标签、reset、RL env、视觉模型；可以按语义分目录。
- `assets/` 放固定资源，例如机器人 USD、场景 USD、材质和模型文件；agent 不得擅自修改。确需修改时，先说明具体文件、影响和风险，并获得用户允许。
- `models/` 放本地训练现场输出，不上传 Git。
- `approved_models/` 放确认保留的模型、配置、trajectory 和说明，需要上传 Git。
- 每次保存实验到 `approved_models/` 时，目录必须尽量自包含：除当前 policy 外，还要放入复现/继续训练所需的视觉预训练、MDP state、teacher 等依赖 checkpoint，并在 `readme.md` 写清楚恢复到默认相对路径的命令。除非用户明确要求拆开保存，否则不得只保存 RL 部分。
- `summary/` 放项目状态、任务流程、TODO、每日总结和共享规则。
- `summary/task_flow.md` 只记录任务流程语义，不放 reward、参数或实现细节。
- 每日总结命名为 `yyyy_mm_dd_{device}.md`；用户要求总结并上传 Git 时，先更新当日总结、`summary/readme.md` 和 `summary/TODO.md`，再按用户确认范围 push。

## 4. 代码实现

- 本项目是研究/学习项目，不按生产工程方式过度设计。
- 改动保持最小，遵循现有架构、命名、格式和工具链；不做无关重构。
- 不写自动找路径、自动加载模型、自动兼容目录结构等工程化兜底逻辑，除非用户明确要求。
- 未经用户明确要求，不得擅自给观测、动作、日志、模型输出或接口增加字段、辅助量、debug 信息或隐含设计。
- 模型、数据、配置默认使用明确相对路径；文件名、模型名默认写死。
- 函数、文件、变量命名简洁清楚，避免冗长。
- 默认使用 ASCII；只有文件已有风格、中文注释需求或业务需要时才引入非 ASCII。
- 回答代码现状问题须以当前真实代码为准，不得凭旧记忆或摘要臆断。
- 旧 Webots 项目只能参考任务语义、标签格式、超参和实验经验；不得照搬旧结构或复杂度。

## 5. 验证与环境

- 完成代码改动后，尽量运行相关的最小验证；影响共享逻辑、用户流程或跨模块契约时扩大验证范围。
- 最终回复必须说明具体验证方式；未验证时直接说明未验证和剩余风险。
- 本项目默认使用 conda 环境 `isaac_test`。
- 不擅自安装依赖、拉取网络资源或改动全局环境；必要时先请求用户批准。
- 非必要不启动 Isaac、Webots 等大型仿真器、图形程序或外部软件；确需启动时先获得用户同意。

## 6. 参考与安全

- `../visual_rlrobot` 为只读参考源，不得修改其任何文件。
- `IsaacLab/` 是第三方依赖；除非确有必要，不阅读其源码，优先依据官方文档和当前项目代码。
- 不泄露密钥、令牌、隐私数据或敏感文件内容。
- 外部事实、价格、法规、版本、新闻、产品行为等可能变化的信息，先查证再回答。

## 7. 多 Agent 协作

- Codex 偏代码实现和少量分析；CC 偏分析、方案和审核。分工不限制用户显式指定的任务。
- 各 agent 有各自私有规则文件；互不读取、修改、删除对方私有规则文件。必要规则只通过对话交换摘要。
- 不得以任何方式间接读取对方私有规则文件内容；仓库级搜索须排除对方私有规则文件。
- plan / state 通信机制当前仍是暂停草案，未定稿前不作为文件修改依据。
- 若用户恢复 plan / state 机制，至少使用 `state` 和 `last_read_line`，避免误读旧消息；具体流程需另行定稿。

## 8. 优先级

规则冲突时，按以下优先级执行：

1. 系统与开发者指令。
2. 用户在当前对话中的明确要求。
3. 各 agent 私有规则文件。
4. 本共享规则。
5. 项目已有代码风格和文档约定。

私有规则不得架空本共享规则中的协作与安全底线，例如 Git 改动保护、不可逆操作确认、固定资源保护和敏感信息保护。
